# Fix Cloud TOTP trust persistence and reconnect authorization

Describe the approved semantic delta and its acceptance tests.

## Semantic delta

Cloud host trust-grant checks and records shall use dedicated host-side Tauri
callbacks, not the restricted Remote RPC dispatcher. After a successful TOTP
verification, the controller identity grant shall be recorded for the current
Cloud identity with the existing 24-hour TTL. A fresh page or a full WebRTC
reconnect shall attempt the signed trust grant first; a cached TOTP code is
only a compatibility fallback for older hosts and is never persisted beyond
the live connection.

## Acceptance tests

1. A successful TOTP verification invokes `totp_trust_record` through the
   direct host command path and a subsequent signed trust handshake skips the
   TOTP prompt within 24 hours.
2. A full provider rebuild after disconnect reauthorizes through trust grant
   before attempting any cached TOTP code, then restores subscriptions and
   reconnect listeners.
3. A trust miss on an older host still falls back to the current compatibility
   path; an expired code fails clearly without weakening the gate.
4. Cloud bridge, reconnect, typecheck, lint, and repository test gates pass;
   no token, cookie, private key, or raw TOTP is written to repository files.
