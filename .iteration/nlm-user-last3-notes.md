### 1. 内核与外壳的权力边界（架构解耦）

你的设想中，**Ridge 内核（Core）** 应成为唯一的「事实真相源（SSOT）」，而外壳（Tauri, TUI, Web）仅负责「状态投影」与「用户输入」。

*   **内核（Ridge Core / Daemon）职责**：
    *   **PTY 生命周期**：统一由 `TerminalManager` 管理，持有所有活动的 PTY 进程、Buffer 和 `scrollback` 内存 [2]。
    *   **终端语义 SSOT**：由 `packages/ridge-term` 驱动的解析与网格管理 [2]。
    *   **工作区物理真相**：负责 `.ridge` 布局文件的 RMW（读-改-写）及 `sidecar` 状态持久化 [3, 4]。
    *   **跨端调度**：处理来自 WebRTC、WebSocket 或 Unix Socket 的多路指令与背压分发 [3]。
*   **外壳（Shells）职责**：
    *   **Tauri 桌面端**：管理 OS 原生窗口（多开）、系统托盘、文件系统权限及平台特定的 `External Binary`（如 `ridge-mcp`）[2, 5]。
    *   **Web Remote**：正如你所言，它通过 `RemoteLink` 直接接入内核的传输层，**完全不经过 Tauri 的 IPC 桥**，这保证了前端状态的彻底隔离 [3]。
    *   **rdg-cli**：作为 TUI 外壳，它与桌面端接入同一套服务内核，共享相同的工作区与 Pane 语义 [1, 6]。

### 2. 多窗口与工作区的「分流行为」

你提到的「桌面端工作区按窗口组合是纯 Tauri 层行为」是一个非常精准的定性。

*   **窗级 active 隔离**：在代码事实中，`a9023f3` 已经实现了 **每个桌面窗口拥有独立的 `selected-workspace` SSOT**，以及按窗口解析的 `native active/layout/ratio` [2, 7]。
*   **内核级全局单例**：虽然 Tauri 层在分流，但内核层保持了 **Remote 工作区跨窗口全局单例** [8]。这意味着：
    *   **桌面端**：通过窗口管理器（Tauri 层）将不同的工作区投影到不同的窗口。
    *   **Web 端**：由于没有窗口管理器的物理限制，它可以直接订阅内核，看到比单个桌面窗口更全的工作区拓扑 [7, 9]。

### 3. 下一步：做好内核（Kernel-First）

要实现你「完完全全做好内核」的目标，当前的 **PROJECT-STATE** 指出了几个关键的结构化残项：

*   **逻辑彻底下沉**：目前的 `close_workspace_core` 和 `rename_workspace_core` 已经实现了部分同源化，但仍需将 `src-tauri` 中残留的 PTY 调度逻辑彻底移入 `packages/ridge-core` [4]。
*   **Daemon 化（IPC 桥接）**：为了让 `rdg-cli` 和桌面端真正接入「同一套服务」，需要实现一个常驻后台的内核进程，使 GUI 和 TUI 成为「无状态」的渲染端。
*   **复合身份与背压调度**：在 `Iteration 75` 中已经合入了 **复合 (workspaceId, paneId) 身份校验** 和 **高低优先级 Writer 调度** [10, 11]。这是内核在高并发、多端接入场景下保持「不丢、不乱、不盲重放」的物理基础 [8]。

### 4. 你的设想对愿景的增强

这个「内核化」方案将直接兑现 Ridge 的北极星目标：
*   **可见**：无论从哪个外壳（Web/TUI/GUI）接入，都能看见 Agent 的同一套运行状态 [1]。
*   **可续**：内核常驻意味着 GUI 的退出或重连不会导致 Agent 任务和 PTY 输出中断 [1, 3]。
*   **可控**：人通过任何一个外壳接入，都能行使「最终裁决权」[1, 3]。

**裁决建议**：我完全支持「先做好内核，再做其他功能」的策略。这符合 **决策过滤器** 中「能否先复用现有能力」和「不引入新状态源」的要求 [12]。后续迭代应优先闭合 **REQ-REMOTE-SMOOTH-STATE-02** 和 **REQ-MOBILE-REMOTE-WORKER-AUTHORITY-01** 涉及的内核级稳定性工作 [11, 13]。

### 1. 纠偏：从「Tauri 侧挂」到「内核原生」
*   **现状缺陷**：当前 `ridge-mcp` 虽然作为独立 binary 存在，但其安装和运行高度依赖 Tauri 的 `external binary` 配置 [2]。在 `REQ-RIDGE-MCP-INSTALLER-01` 中，它的定位更多是「桌面安装包的捆绑附件」，而非独立的系统服务 [2]。

为了实现你「Agent 相互定位与交流」的愿景，`ridge-mcp` 的逻辑应下沉至以下模块：

*   **基于 `teammate` 服务的路由**：目前 **`teammate server`** 已经实现了跨工作区的 `roster`（成员名单）聚合 [6, 8]。`ridge-mcp` 应当直接向内核中的 `teammate` 服务发起请求，通过已有的 **`agent_id`** 或 **`sessionId`** 进行精准寻址，而不是通过 UI 层面的「当前激活窗口」来猜测目标 [7, 9, 10]。
*   **利用 `tmux` 垫片实现「拉起与定位」**：
    *   **拉起新终端**：应复用已有的 `StructuredPtyCommand` 逻辑，由内核直接通过 PTY master 创建新 Pane，并注入 **`RIDGE_PANE_ID`** [6, 7]。

### 3. 下一步：纠正 MCP 的「生存空间」
正如你设想的「内核彻底拆除」，`ridge-mcp` 的下一步改进不再是优化 UI，而是：
1.  **协议迁移**：将 `ridge-mcp` 的后端接入点从 Tauri Command 迁移到内核的 **Unix Socket / Daemon 接口** [13]。
2.  **能力注入**：使 `ridge-mcp` 具备调用 **`launch_agent_session`** 的权限，从而实现从命令行或另一个 Agent 内部「物理拉起」新终端的能力 [7, 9]。
3.  **身份锚定**：强制所有经由 MCP 启动的会话携带完整的 **`composite identity`**，确保在多窗口或多端（Web/TUI）接入时，Agent 的位置信息始终是 SSOT（唯一事实来源） [14-16]。

**裁决建议**：目前的 `ridge-mcp` 确实「做错了」，它不应是桌面的「随从」，而应是 **内核暴露给外部 Agent 的标准接口（API Surface）**。我建议你在完成内核 Daemon 化后，第一时间重写 `ridge-mcp` 的连接器，使其通过 **`teammate` 服务** 彻底实现你所说的 Agent 间互感与协作 [3, 17, 18]。
