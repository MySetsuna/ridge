### 1. 现状：正在成型的「Ridge 内核」
目前的架构已经将大量核心能力下沉到 **`packages/`** 下的独立模块中，为你的「纯净内核」目标提供了物理基础：
*   **终端语义内核 (`ridge-term`)**：作为解析、网格管理和 Scrollback 的 **SSOT（唯一真相源）**，它不依赖于任何 GUI 框架 [1, 2]。
*   **统一实例管理器 (`TerminalManager`)**：这是内核的心脏，负责统一 PTY 实例的生命周期。目前桌面端、Remote 端（Web）甚至未来的 `rdg` 都在复用这一套逻辑 [1]。
*   **状态与通信层 (`ridge-core` / `RpcClient`)**：承接了工作区、窗格、Git 命令及异步分发（dispatch）[1]。最新的 `5eece08` 提交还为 RPC 引入了 256 在途硬上限与超时诊断，这标志着通信层已具备内核级的健壮性 [3]。

### 2. 内核能力的归位（解耦清单）
针对你提到的具体能力，目前的实现进度与解耦方向如下：
*   **文件系统与 Git 管理**：
    *   **现状**：`SourceControl` (SCM) 已经实现了共享的非 Git 缓存，其状态、分支和心跳逻辑已开始共用仓库真值 [3]。
    *   **内核化方向**：正如你所设想，`git_output` 和 `run_command_with_timeout` 已经在内核层实现了 Windows 进程树清理和硬护栏，确保了在无 GUI 环境下执行 Git 动作的安全性 [4]。
*   **Agent 管理、编组与历史**：
    *   **现状**：`teammate server` 已经实现了跨工作区的 roster（成员名单）聚合 [1]。Agent 历史也已改为按 **原生 Session ID** 聚合，不再依赖 UI 层的路径猜测 [5, 6]。

*   **远端接入与设置**：
    *   **现状**：最新的 **复合身份 `(workspaceId, paneId)`** 校验确保了 Remote 接入不再回读 Tauri 的活动工作区状态，实现了「端到端」的身份锁定 [3, 9]。
    *   **内核化方向**：Web Remote 目前已通过 `RemoteLink` 直接接入内核传输层，完全不经过 Tauri 桥 [10, 11]。

### 3. 症结确认：为何 `rdg` 始终不可用
你关于「解耦不足导致 `rdg` 不可用」的直觉完全正确。
*   **资源归属权问题**：过去部分 PTY 生命周期被隐式挂载在 Tauri 的窗口事件（如 `onDestroy`）上，导致无头模式下 PTY 进程容易被宿主意外杀死或无法正确初始化。
*   **真相源冲突**：如果内核没有彻底 Daemon 化，`rdg` 与桌面端就会竞争同一个 `.ridge` 布局文件的写权限，导致 **双 SSOT 债务** [12]。
*   **无头 Session 盲区**：目前 **REQ-HEADLESS-DETECTION-02** 正在解决的问题正是如何让内核（而非 Tauri）准确识别并召唤那些已脱离 UI 掌控的原生进程 [13, 14]。

### 4. 下一步：走向「单一内核」的执行策略
你提出的「完完全全做好内核」是当前最高优先级的动作（**REQ-20260730-01**）[15]：
1.  **彻底下沉逻辑**：将 `src-tauri` 中残留的 PTY 调度、设置读取和工作区 RMW 逻辑搬迁至 `packages/ridge-core`。
2.  **Daemon 化接入**：实现一个常驻后台的 `ridge-daemon`。Tauri（桌面端）、`rdg`（CLI）和浏览器（Remote）都将作为这个 Daemon 的 **「无状态客户端」** [1, 16]。
3.  **窗口分流逻辑外壳化**：保留你在 `a9023f3` 中实现的窗口级 active 隔离，但将其定义为 **「纯外壳层的视图分流」**。内核只负责维护全局的工作区拓扑，而不关心该工作区是被哪个窗口认领的 [1, 3]。

**最终结论**：你的设想与 Ridge 的 **北极星指标（可见/可控/可续/可协作）** 完全契合 [17]。内核化后的 Ridge 将不再是一个简单的桌面 App，而是一个可以随处挂载、具备完整协作能力的开发控制平面。我将根据你的指令，在接下来的迭代中优先确保内核的彻底独立与稳定性。

### 7. 跨账号单工作区分享 (REQ-WORKSPACE-SHARE-01)
*   **优先级**：**P1/P2** (扩展能力)
*   **用户可观察目标行为**：Owner 可通过菜单分享单个工作区给其他用户；受邀者在侧栏看到“共享：工作区名”，仅能操作授权范围 [13]。
*   **范围与非目标**：Cloud 授权、Scoped JWT、受限资源投影；**非目标**为匿名分享或全主机授权 [14]。
*   **确定性验收标准**：受邀者无法访问同 Host 的其他工作区；撤销授权后立即踢线；Viewer/Operator 权限控制准确 [14]。
*   **对应 ID**：REQ-WORKSPACE-SHARE-01, R62-WS-SHARE [2, 13]。

### 8. 自动对比度研究 (REQ-AUTO-CONTRAST-RESEARCH-01)
*   **优先级**：**P2** (辅助研究)
*   **用户可观察目标行为**：仅在视觉实验环境中通过原型验证文字可读性切换方案，**不授权**全局产品部署 [15]。
*   **确定性验收标准**：输出包含性能评估与 WCAG 标准的方案报告；触发停机条件（如无法避免布局抖动）则归档为 Deferred [15]。
*   **对应 ID**：REQ-AUTO-CONTRAST-RESEARCH-01 [15]。
