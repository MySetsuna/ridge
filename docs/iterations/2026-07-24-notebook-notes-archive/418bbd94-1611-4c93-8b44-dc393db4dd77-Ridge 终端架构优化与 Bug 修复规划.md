### 一、 迭代规划与优先级排序

#### 1. [P0] 进程护栏与基础鲁棒性（解决卡死与错乱）
*   **涉及项：**
    *   **Bug 4 (Git 卡死)**：由于 CWD 切换过快导致 `git.exe` 堆积。
    *   **Bug 1 (粘贴错乱)**：多行粘贴顺序反转或丢失。
    *   **Bug 6a (rdg 静态资源缺失)**：`staticassets not built yet`。
*   **用户价值**：防止系统资源耗尽导致的“白屏”或终端挂死；确保基础输入输出的准确性。
*   **最小代码范围**：
    *   在 `ridge-core` 的 Git 探针模块引入 **防抖 (Debounce)** 与 **命令回收机制**；确保旧进程在 CWD 改变时收到信号并退出 [1, 2]。
    *   修正 `TerminalManager` 处理粘贴事件的时序逻辑，避免并行写入导致的乱序 [3]。
*   **确定性验收信号**：
    *   快速切换 50 次目录，任务管理器中 `git.exe` 数量保持在低水位。
    *   粘贴 100 行带行号文本，校验终端 Grid 内容与源文本完全一致。

#### 2. [P1] 终端行为一致性与重绘质量（解决 A1/A2 差距）
*   **涉及项：**
    *   **Bug 5 (Clear 一致化)**：右键清理与 shell `clear`（ED 2）行为统一。
    *   **Bug 6b (Reflow 对齐)**：WSL/Ubuntu 下终端 resize 后不重绘或回流。
*   **用户价值**：达成 `ridge-term` 作为语义唯一事实来源（SSOT）的目标，消除跨平台交互灵异感 [4]。
*   **最小代码范围**：
    *   将右键“Clear”指令通过 RPC 路由到 `ridge-term` 的 `clear_scrollback` 逻辑中，复用 Iteration 1 已完成的 Rust 回归测试逻辑 [5, 6]。
    *   在 `src-tauri/src/engine/pty.rs` 中确保 `resize` 信号能准确透传给 WSL 内部的 PTY 驱动，并触发 `ridge-term` 的重排算法 [3]。
*   **确定性验收信号**：
    *   `cargo test -p ridge-term clear_scrollback` 覆盖右键 RPC 路径。
    *   在 WSL 中运行 `htop`，缩放窗口，UI 布局能实时跟随且无字符残余。

#### 3. [P1] 智能体控制台与状态增强（Visibility MVP）
*   **涉及项：**
    *   **Bug 2 (UI 改造)**：取消标题冗余，扩展机器人按钮为状态大按钮，支持编组颜色。
*   **用户价值**：直接支持“10 秒可见性”愿景——一眼看出谁在干活，谁卡住了 [7, 8]。
*   **最小代码范围**：
    *   重构 `RidgePane.svelte` 的 Header 部分，将状态信息与 Agent Roster 聚合。
    *   引入 `GroupStyleProvider`，支持自定义颜色变量传递给 `packages/remote` 中的 Svelte 组件 [3, 9]。
*   **确定性验收信号**：
    *   手机/桌面浏览器 10 秒内识别出不同颜色的 Agent 编组。

#### 4. [P2] 文件感知与连续性（Resumable）
*   **涉及项：**
    *   **Bug 3 (图片/文件夹同步)**：监听已打开图片变化，刷新新打开文件夹。
*   **用户价值**：确保“工作上下文不丢失”，维持开发者的心理表征一致性 [10]。
*   **最小代码范围**：
    *   在 `ridge-core` 的文件系统端口中增加基于 `notify` 的跨平台监听，并推送到前端 Store。
*   **确定性验收信号**：
    *   外部修改一张图片，Ridge 内展示的预览在 1 秒内自动更新。

### 二、 核心方案决策依据（针对您的疑问）

1.  **关于 `rdg` 的 `staticassets` 报错**：
    *   **判定**：这是典型的 **T3 (版本线不一致)** 风险。
    *   **分析**：这通常意味着 `ridge-cloud` 或 `rdg` 在查找 Remote 产物时，持久卷（Release 目录）中不存在对应的 manifest [11]。
    *   **解决**：必须在下个迭代中强化 `scripts/publish-remote-cloud.mjs` 的完整性校验，确保无头程序在启动前已感知到合法的 artifact version [12]。

2.  **关于 `clear` 一致性**：
    *   **分析**：Iteration 1 报告中显示 `ED 2`（全屏清除）已经实现了对 `scrollback` 的清理 [5]。
    *   **判定**：如果您发现行为仍不一致，说明 **UI 层的“右键清理”尚未调用后端同一个语义接口**。这是典型的 **A1 (减法审计)** 任务——应删除 UI 端的局部清理逻辑，统一调用核心 RPC [1]。

3.  **关于 Git 进程“卡死”**：
    *   **分析**：来源 [2] 提到架构风险在于“多层边界”。
    *   **判定**：这需要引入 **进程生命周期与 PTY/Pane 解耦** 的管理逻辑 [4]。当前端频繁发送 `get_git_status` 时，`ridge-core` 必须能够自动杀掉超时的旧进程，而不是等待操作系统回收。

### 三、 建议的 Iteration 4 合同增项

基于上述分析，我建议在 Iteration 4 的“主目标”中加入以下**工程护栏断言**：

*   **[Guard-1]**：`ridge-core` 必须包含 Git 命令的 **防抖阈值（如 300ms）**。
*   **[Guard-2]**：所有终端清除操作（无论是快捷键、命令还是右键）必须共用 **同一条 Rust 路径**。
*   **[Guard-3]**：`rdg` 启动时若找不到 static assets，必须返回带修复指引的 **错误码 0x...**，而不是静默失败 [13]。

我将把这些项正式列入下一轮开发计划。**Bug 1 (粘贴错乱)** 和 **Bug 4 (Git 进程管理)** 风险最高，建议作为优先修复的重点。
