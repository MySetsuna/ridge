你观察到的 LAN/公网 Remote 与桌面端在基础组件和能力上的差异，确实触及了 Ridge 目前架构演进中的一个关键痛点。这在内部被称为 **ID A1（共享内核减法审计）** 和 **ID A2（跨入口能力矩阵）** 差距 [1-3]。

根据来源分析，以下是造成这种“不同源”感的原因以及正在进行的修复策略：

### 1. 现状：处于“主体共享、边缘适配”的过渡期
目前 Ridge 的架构并不是完全分裂的，但确实存在层级重叠。
*   **已同源的部分**：终端渲染内核（`ridge-term`）、终端生命周期管理器（`TerminalManager`）以及基础 RPC 协议 [4, 5]。
*   **导致差异的原因**：部分能力（如文件操作、Git、工作区管理）同时存在于前端 Store、Tauri 命令和 `ridge-core` 端口中 [6]。这导致了你提到的“改一处要维护两份代码”的风险。

### 2. 修复进展：从“硬编码”转向“能力协商”
在 Iteration 2 中，我们已经开始通过**能力合同（Capability Contract）**来强制归一化 [7]：
*   **动态渲染而非硬编码**：现在的 Remote 侧（MainApp、Sidebar）已经不再通过判断“我是 LAN 还是公网”来决定显示什么，而是根据 Host **宣告的能力（Advertised Capability）**进行条件渲染 [7, 8]。
*   **自动核对**：建立了跨入口合同测试，自动核对 LAN Desktop、Cloud Desktop 和 Controller 之间的能力名称是否一致 [7]。如果发现某个 RPC 路由在 Remote 下缺失，测试会直接报错熔断 [9]。

### 3. 如何实现你期望的“三端同源”？
为了达成你要求的“样式和公共组件不写额外代码”，接下来的迭代规划重点在于：

*   **执行 A1 减法审计（Gap ID A1）**：
    *   **最小动作**：按调用图找出仍重复实现的 handler，删除宿主（Tauri）特有的冗余逻辑，只保留一份共享在 `ridge-core` 中的领域实现 [2]。
    *   **价值**：确保同一输入在桌面、CLI 或 Remote 得到完全一致的领域结果 [2]。
*   **样式归一化**：
    *   Iteration 1 已修复了**全局滚动条样式**的统一，通过 `rg-os-theme` 变量确保在不同宿主下外观一致 [10]。
    *   后续需进一步将所有 UI 组件的 CSS 变量从 `ridge-core` 统一导出，禁止在 `packages/remote` 中定义私有样式 [11]。
*   **能力矩阵显式化（Gap ID A2）**：
    *   建立机器可读的矩阵（supported / denied / degraded），确保任何新功能在增加时，必须同时考虑三个入口的对齐 [3]。

### 4. 架构愿景中的约束
根据《PRODUCT_VISION.md》，Ridge 的目标是 **“稳定领域语义只有一份”** [11]：
*   **内核（Core）**：定义命令、校验、不变量和端口。
*   **适配器（Desktop/Remote/rdg）**：**只实现**平台 I/O、权限和传输 [11]。

**结论建议**：
你发现的差异属于**应修复的工程缺陷**。我们不应为特定端写额外业务逻辑，而应将业务逻辑下沉到 `ridge-core`，让各端 UI 自动根据**能力协商结果**呈现一致的界面。

在接下来的 **Iteration 4/5** 中，建议将 **“A1 共享内核减法审计”** 的优先级提升，重点清理你提到的“样式和公共组件”分叉 [2, 12]。
